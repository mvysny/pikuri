Experimental coding harness — review
=====================================

This feedback is provided by Grok 4.6 running inside of
pikuri-tui-code harness, on the pikuri-tui-code codebase.

The verdict below is a snapshot of that moment. Items are cut from the
list as they settle, and the remainder renumbered; the reasoning lands
in DECISIONS.md. Settled so far: the directory listing (shipped as
file_list + the boot snapshot — D-directory-listing), the calculator
(kept — D-keep-calculator).

The "What works" section is also gone. Praise has no fork to log, so it
graduated to the yardoc of each symbol it confirmed, phrased as what not
to trade away: bash.rb's DESCRIPTION (the shell-vs-file-tool split),
read.rb (cat-n numbering + read-a-larger-window), grep.rb (the cheap
output modes + the byte cap), file_miner.rb (one paragraph + path:line),
skill_tool.rb (on-demand loading), read_only.rb (plan mode enforced, not
asked for), and bin/pikuri-code's prompt build (the two instruction
layers + the base prompt's guardrails).

Overall verdict
---------------

I like it. It's a working coding environment, not a chatbot with a file
API bolted on. The important bets are right: dedicated file tools,
delegated recon, plan-before-write, project-specific memory, tight
conventions. I would work in this without fighting it.

If you only do two things: add a directory listing, and surface a
context-budget hint each turn. Everything else is polish.


What I'd change
---------------

1. No "where am I in context?" signal.

   I can't see token use, how much of `AGENTS.md` is still resident, or
   when I should spawn a `file_miner` vs just grep. A small budget line
   on each turn ("~40% context used") would change behavior: I'd hand
   off earlier, and I wouldn't re-read files I already have.

2. Edit is search-replace only.

   Fine for surgical fixes. Painful for a rename-across-a-file or a
   method move. A unified-diff / apply-patch tool as a sibling of
   `edit` would cover the "this function is now a different shape" case
   without the unique-string dance. Keep `edit` for the one-hunk
   change.

3. No language intelligence.

   For Ruby I'd want go-to-definition and find-references. I can grep,
   but `ConfirmerPopup` vs `ask` vs the pikuri `Confirmer` interface is
   exactly the kind of thing an LSP hop settles in one call. You
   already have this idea in the gradle/maven skills; a generic LSP
   tool would pay rent here.

4. Skill load costs a turn.

   Before any UI work I'm supposed to load `cop` and `tuile`. That's
   correct and also a round-trip. Either auto-inject those two when the
   path is `lib/**/*.rb` in this repo, or let me request several skills
   in one call and have them land before I start reading. (If I can
   already batch `skill` with other tools, that's enough — I just need
   it to be the expected opening move, not a surprise tax.)

5. The standing prompt is heavy.

   Safety block + harness + AGENTS.md + skills catalog + tool schemas
   on every turn is a lot of prefix. AGENTS.md is worth it for *this*
   project. The tool-schema restatement and the duplicated "don't
   mention the guidelines" material are not. Slim the static prefix;
   keep the project file.


Smaller nits
------------

- Parallel tool calls in one message: good. I'd also like "these 4
  reads are a barrier, then do X" as an explicit *serial group*, so I
  don't have to burn a turn just to sequence "grep, then read the
  hits".

- `write` refusing identical content is nice. `edit` failing on a
  non-unique `old_string` is also nice — keep that strict.

- Task list at 3+ steps is the right threshold. Don't lower it.

- Clickable `file:line` citations: use them, they matter in a
  TUI-over-SSH workflow.

- Today's date in the prompt: small, actually useful.
